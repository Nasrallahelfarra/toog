# طوق — المستشار الذكي لمنتجات التجارة الإلكترونية

منصة تقيّم كل منتج أو تصميم جديد قبل طرحه مقابل مبيعات المتجر وتوجهات السوق السعودي، وتوصي بالقبول أو الرفض أو التعديل، وتولّد تصاميم بهوية المتجر.

## التقنيات

| الطبقة | التقنية |
|---|---|
| الخادم | Laravel 13 (PHP 8.3+) + Fortify (تسجيل الدخول، التحقق بخطوتين، مفاتيح المرور) |
| الواجهة | React 19 + TypeScript عبر Inertia 3 (مشروع واحد) + Tailwind 4 + shadcn/ui + Motion + Recharts |
| قاعدة البيانات | SQLite محليًا — MySQL أو PostgreSQL في الإنتاج بتغيير `.env` فقط |
| الذكاء الاصطناعي | Gemini (التحليل والصور) عبر طبقة `App\Services\Ai\Ai` مع تسجيل التكلفة لكل استدعاء |
| المهام الخلفية | Laravel Queues + Scheduler (المزامنة، رصد المنافسين، التقييم، توليد التصاميم) |
| التصدير | PhpSpreadsheet (Excel) وصفحات طباعة PDF تدعم العربية |

## التشغيل محليًا

```bash
composer install
npm install
cp .env.example .env        # إن لم يكن موجودًا
php artisan key:generate
php artisan migrate

php artisan storage:link
composer dev                # الخادم + الطوابير + Vite معًا
```

افتح http://localhost:8000

### إضافة بيانات التجربة على سيرفر موجود

بعد الخروج من Tinker بكتابة `exit`، نفّذ من مجلد المشروع:

```bash
git pull origin main
php artisan migrate --force
php artisan db:seed --force
php artisan storage:link
```

السيدر يضيف المتاجر التجريبية الناقصة، ويتجاوز المتجر التجريبي الموجود مع الحفاظ على بياناته. يتعرف على المتاجر القديمة من حساب المالك مع الاسم أو النطاق، وعلى الجديدة من علامة داخل إعدادات المتجر. لا يغيّر كلمات مرور الحسابات الموجودة أو إعدادات التقويم المعدّلة، ولا يحذف صور التصاميم والتقييمات. كلمة المرور `password` تخص الحسابات التجريبية التي ينشئها لأول مرة فقط.

إذا أنشأت حساب تجربة يدويًا وله متجر مختلف، يضيف السيدر متجر التجربة إلى نفس الحساب مع إبقاء كلمة مروره ومتجره الحالي. يولّد السيدر الصور والتحليلات التجريبية محليًا دون استهلاك رصيد Gemini، ويحفظ بيانات كل متجر جديد ضمن معاملة مستقلة. يمكن تكرار الأمر دون تكرار البيانات. المتاجر الموجودة، بما فيها بيانات تجربة جزئية من تشغيل قديم، لا يعيد تعبئتها حفاظًا على تعديلاتك.

هذا يضيف نفس أنواع بيانات العرض التجريبي؛ لا ينسخ قاعدة بيانات اللوكل ولا نتائج فحص المنافسين التي أجريتها عليها. لا تستخدم `migrate:fresh` عند الرغبة في الحفاظ على البيانات الحالية.

## الإعدادات (`.env`)

```env
APP_NAME="طوق"
VITE_APP_NAME="${APP_NAME}"

# Gemini — بدون مفتاح تعمل المنصة في «وضع العرض التجريبي» (نتائج قوالب وصور توضيحية بلا تكلفة)
GEMINI_API_KEY=
GEMINI_TEXT_MODEL=gemini-3.8-flash
GEMINI_IMAGE_MODEL=gemini-nano-banana-2.1

# زد — من لوحة شركاء زد
ZID_CLIENT_ID=
ZID_CLIENT_SECRET=
ZID_REDIRECT_URI="${APP_URL}/store/integrations/zid/callback"
```

أسعار النماذج المستخدمة في حساب التكاليف موجودة في `config/mojo.php` (`ai.pricing`).

للتحويل إلى MySQL/PostgreSQL: غيّر `DB_CONNECTION` وبيانات الاتصال ثم `php artisan migrate`.

في الإنتاج شغّل عامل الطوابير (`php artisan queue:work`) والمجدول (`php artisan schedule:run` كل دقيقة عبر cron).

لتطبيق الاسم الجديد على سيرفر موجود، عدّل `APP_NAME` و`VITE_APP_NAME` في ملف `.env` على السيرفر كما في المثال أعلاه، ثم أعد بناء الواجهة وتحديث الإعدادات وعامل الطوابير:

```bash
npm ci
npm run build
php artisan config:cache
php artisan view:clear
php artisan queue:restart
```

## الأدوار

- **مدير المنصة**: يطّلع على كل المتاجر وتفاصيلها، وتكاليف الذكاء الاصطناعي، والمستخدمين (تفعيل/تعطيل/إعادة تعيين كلمة المرور)، وإيقاف المتاجر وميزانياتها، وسجل النشاط، وإعدادات المنصة — ويستطيع **دخول لوحة أي متجر بصلاحيات المالك الكاملة** (تُسجَّل أفعاله كـ«مدير»).
- **صاحب المتجر**: لوحة متجره بكل الأدوار الواردة في نطاق العمل (مدير المنتجات، المصمم، التسويق، مسؤول النظام للمتجر).

البنية جاهزة لإضافة الأدوار الأخرى لاحقًا (جدول `store_user` بعمود `role`).

## ملاحظات

- يُحسب مؤشر الملاءمة بقواعد ثابتة من خصائص المنتج والبيانات المتاحة. يضيف Gemini مراجعة متخصصة للتصميم والسوق والجمهور مع توصيات وأدلة وثقة منفصلة؛ المؤشر ليس احتمال نجاح أو نسبة مبيعات.
- مسارات واجهة زد البرمجية (المنتجات والطلبات) مجمّعة كثوابت في `app/Services/Zid` ويجب مطابقتها مع توثيق زد عند الحصول على بيانات التطبيق.
- رصد المتاجر يجمع الكتالوج العام لـ Shopify أو بيانات المنتجات المنظمة في صفحات المواقع الأخرى. قد تحتاج بعض المواقع إلى محوّل خاص؛ شبكات التواصل تحتاج ربطًا منفصلًا.

## تجربة تحليل منافس

### HTTPS والنشر على Laravel Cloud

على Laravel Cloud، اضبط متغيرات بيئة `production` من لوحة Cloud ثم أعد نشر أحدث نسخة من `main`. مثال عنوان هذه البيئة:

```env
APP_URL=https://toog-production-nitj3p.laravel.cloud
ASSET_URL=https://toog-production-nitj3p.laravel.cloud
```

استخدم عنوان بيئتك الفعلي عند تغيير النطاق. يمكن حذف `ASSET_URL` إذا لم تستخدم نطاق ملفات منفصلًا؛ لا تتركه بقيمة `http://`. يحافظ `bootstrap/app.php` على تعرّف Laravel التلقائي على بروكسي Cloud، مع إبقاء دعم ngrok المحلي. بهذا تبقى روابط CSS وJavaScript والخطوط والتحويل إلى تقرير المنافس على HTTPS.

في Cloud تُحفظ المتغيرات من لوحة البيئة وتُطبّق بإعادة النشر. ضع `php artisan config:cache` ضمن Build Commands إذا أردت التخزين المؤقت للإعدادات؛ تغييرات الملفات في Deploy Commands أو طرفية السيرفر ليست بديلًا عن نشر نسخة جديدة. Cloud يعيد تشغيل العمال عند النشر. راجع [إعدادات البيئات في Laravel Cloud](https://laravel.com/cloud/docs/environments).

### التخزين على Laravel Cloud

تتضمن اعتماديات الإنتاج حزمة `league/flysystem-aws-s3-v3` المطلوبة لإرفاق Object Storage bucket. يجب نشر `composer.json` و`composer.lock` معًا؛ تثبيت الحزمة من طرفية السيرفر وحده لا يحفظها للنشر التالي.

تستخدم الصور والشعارات والتصاميم في المشروع `Storage::disk('public')`. عند ربط البكت المخصص لهذه الصور بالبيئة، اضبط **Disk name** على `public`. جعل قرص باسم آخر هو الافتراضي لا يغيّر استدعاءات `disk('public')`. يحقن Laravel Cloud إعدادات الاتصال تلقائيًا عند النشر، بما فيها رابط الملفات للبكت العام.

لعرض الصور بالروابط المباشرة الحالية يحتاج البكت المخصص لها إلى **Public visibility**. البكت الخاص يحتاج روابط مؤقتة أو تقديم الملفات عبر مسار مصادق عليه، وهو مسار مختلف عن عرض الصور الحالي. لا تضف `visibility=public` إلى إعدادات S3 يدويًا؛ Cloudflare R2 يدير الإتاحة على مستوى البكت. راجع [توثيق Laravel Object Storage](https://laravel.com/cloud/docs/resources/object-storage).

بعد حفظ إعدادات البكت انشر أحدث نسخة من `main`. ربط البكت لا ينقل الصور الموجودة سابقًا على القرص المحلي؛ تحتاج الملفات القديمة إلى نسخ منفصل إن كانت ما تزال متاحة.

### بدء الفحص

من «المنافسون» اختر «إضافة منافس»، ثم «موقع متجر (كشف تلقائي)»، وأدخل الرابط. الاسم اختياري. بعد الحفظ اضغط «فحص الآن» وافتح تبويب «التقرير».

الفحص يعمل بالخلفية ويفتح لوحة تقدم تتحدث كل ثانيتين. النسبة تعبّر عن اكتمال خمس مراحل (التحقق من القراءة، الواجهة، المنتجات، الحفظ، التقرير)، وليست تقديرًا للوقت المتبقي. تظهر الصفحات والمنتجات المرصودة، ويظهر التقرير تلقائيًا عند توفره. تبقى البيانات المقروءة متاحة أثناء انتظار جمني. يمنع تكرار النقر تشغيل فحصين لنفس المنافس، ويمكن الرجوع للصفحة لمتابعة الطلب أو إعادة المحاولة بعد الفشل.

مثال التجربة: `https://theblueage.com/en` (Blue Age، ملابس في السعودية).

- يحفظ الفحص عينة من المنتجات والأسعار ومصادرها وتاريخ الرصد. حد Shopify: أول 100 منتج، وحتى قسمين معلنين للأكثر مبيعًا، بحد 24 منتجًا لكل قسم. المواقع الأخرى: بيانات المنتجات المنظمة وأربع صفحات منتجات مرتبطة كحد أقصى.
- «الأكثر مبيعًا» يستند إلى عضوية قسم يعلن المتجر عنه بهذا الاسم؛ ترتيب الكتالوج وحده ليس دليلًا. البروز في الرئيسية يعني ترويجًا داخل الموقع، وليس عدد الإعلانات أو المبيعات.
- تبقى المبيعات غير المتاحة مجهولة. إذا نشرت بيانات المنتج المنظمة عدّاد `unitsSold` أو `salesCount`، يحفظ نصه ومصدره؛ عدد المراجعات لا يُحوّل إلى مبيعات.
- يستخدم جمني الأدلة المرصودة لتقديم تحليل مستقل. إذا غاب المفتاح أو فشل الطلب، تبقى البيانات الحقيقية متاحة وتظهر حالة التحليل دون إنشاء ملخّص وهمي.
- يحترم الفحص قواعد `robots.txt`، ويقيّد عدد الطلبات وحجمها، ويرفض عناوين الشبكات الداخلية. يوضح التقرير الصفحات المتعذرة وحدود التغطية.

لتحديث سيرفر موجود، اسحب التغييرات ثم نفّذ:

```bash
php artisan migrate --force
npm ci
npm run build
php artisan config:cache
php artisan view:clear
php artisan queue:restart
```

يحتاج الفحص إلى عامل طوابير يعمل باستمرار. لإعداد الطابور المعتاد ضع في `.env`:

```env
QUEUE_CONNECTION=database
DB_QUEUE_RETRY_AFTER=660
```

بعد تعديل الإعدادات نفّذ `php artisan config:cache`. للتجربة شغّل الأمر التالي من طرفية أخرى واتركها مفتوحة أثناء الفحص:

```bash
php artisan queue:work --sleep=1 --tries=1 --timeout=600
```

في التشغيل الدائم شغّله من مدير العمليات في الاستضافة أو Supervisor مع إعادة التشغيل تلقائيًا. `queue:restart` يعيد تشغيل العامل الموجود ولا ينشئ عاملًا جديدًا. إذا بقيت الواجهة «بانتظار بدء المعالجة» فتأكد من تشغيل العامل على نفس المشروع وقاعدة البيانات والطابور. تنتهي صلاحية الطلب الذي لم يبدأ بعد 15 دقيقة، والفحص الذي تجاوز مهلة العامل بعد 11 دقيقة، لتتاح إعادة المحاولة. عند استخدام Redis أو Beanstalkd اجعل `retry_after` أطول من مهلة المهمة (الافتراضي الجديد 660 ثانية).

لتحليل جمني اضبط `AI_PROVIDER=gemini` و`GEMINI_API_KEY` في `.env` على السيرفر، وتأكد من توفر رصيد API. هذه الترقية لا تحتاج إعادة تشغيل السيدر.

## مراجعة المنتج وتطبيق التحسينات

تتضمن صفحة التقييم مراجعة متخصصة لجودة التصميم وملاءمة السوق والجمهور. أضف الجمهور المستهدف عند إنشاء التقييم. تستند المراجعة إلى الصورة وبيانات المتجر وعينة من منافسي الفئة والاتجاهات المخزنة، وتعرض الأدلة والمعلومات الناقصة ومستوى الثقة. بيانات المتاجر التجريبية تُوسم بوضوح ولا تُقدّم كدليل مبيعات حقيقية. يمكن طلب مراجعة للتقييمات القديمة من صفحتها؛ لا تتغير تلقائيًا.

يختار المستخدم توصيات بصرية ثم يضغط «تطبيق التحسينات المختارة». تُحفظ التوصيات المختارة مع نسخة من بيانات المصدر، وتُنشأ صورة مستقلة ثم يقارن المراجع الصورتين ليتحقق من كل تعديل والحفاظ على بقية تفاصيل المنتج. التوصيات المتعلقة بالسعر والتصنيع والتجارب التجارية تبقى إجراءات لصاحب المتجر. لا تتغير الصورة الأصلية ولا يُنشر المنتج تلقائيًا؛ اعتماد النسخة يختار التصميم فقط، وقرار اعتماد المنتج يبقى في لوحة القرار.

يظهر تحميل داخل إطار الصورة أثناء انتظار التوليد وتنفيذه، ثم تظهر الصورة فور جاهزيتها مع حالة مراجعتها. بعد الاكتمال يفتح زر «إعادة توليد بتعديل مخصص» نافذة تعرض الصورة التي ستُعدّل وحقلًا لوصف التغيير. يُطبق الطلب على هذه النسخة المولّدة، وتُحفظ النتيجة ومراجعتها كنسخة لاحقة مع بقاء النسخ السابقة واعتمادها. يُمنع تكرار الطلب أو تشغيل تعديلين متزامنين لنفس التقييم.

الصورة الجديدة تُراجع من محتواها الفعلي، وتُحفظ كنسخة تقييم ضمن نفس سجل المنتج، بدل احتساب خصائص التعديل المطلوب وكأنه تحقق. يظهر التنفيذ الجزئي والتغييرات غير المطلوبة، ويحتاج اعتماد نسخة ذات ملاحظات إلى إقرار المستخدم. لا يُفترض أن الدرجة الجديدة ستزداد. إذا فشل الفحص بعد التوليد، يعيد زر المحاولة الفحص فقط مع الاحتفاظ بالصورة؛ الطلبات المكررة لا تبدأ توليدًا موازيًا.

للنشر: نفّذ `php artisan migrate --force` ضمن Deploy Commands وابنِ الواجهة، مع تشغيل عامل الطابور المذكور أعلاه. تبقى أسماء النماذج قابلة للتغيير عبر `GEMINI_TEXT_MODEL` و`GEMINI_IMAGE_MODEL`. يستخدم المسار [مخرجات Gemini المنظمة](https://ai.google.dev/gemini-api/docs/structured-output) للمراجعة و[تحرير الصور](https://ai.google.dev/gemini-api/docs/image-generation) للتنفيذ. صور PNG/JPEG/WebP حتى 8 MiB مدعومة في هذا المسار. غياب جمني أو فشل المراجعة يظهر كحالة غير متاحة، ولا يُستبدل بفحص أو صورة تجريبية تدّعي نجاح التحسين.

تُقسّم المهمة إلى توليد (مهلة 300 ثانية) ثم مقارنة وتقييم (600 ثانية)، مع `retry_after` أكبر من المهلة. تظهر حالات الانتظار والتعديل والفحص مباشرة في الصفحة، وتنتهي المهام المهجورة بعد 15 دقيقة. التوصيات بشأن استجابة العملاء فرضيات تحتاج اختبارًا عمليًا، والمؤشر الحسابي ليس احتمال نجاح تجاري.
